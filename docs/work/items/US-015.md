### US-015: Harden the origin server and site response hygiene
**As a** visitor and site owner, **I want** the origin to send modern security headers, redirect www to apex, refuse dotfiles, and serve a branded 404 **so that** the site does not leak files or lack baseline browser protections.
**Points:** 5
**Status:** Done
**Acceptance criteria:**
- [x] Given any request served by `server/contact.py`, when the response arrives, then `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, and `Permissions-Policy` headers are present, with a CSP shipped in `Content-Security-Policy-Report-Only` mode
- [x] Given a request whose Host is `www.tetrazero.com`, when any path is requested, then the origin responds 301 to `https://tetrazero.com` + the original path and query
- [x] Given a request for a dotfile such as `/.htaccess`, when the origin handles it, then it returns 404 instead of serving the file
- [x] Given a request for a path not in `dist/`, when the origin responds, then it returns the built `404.html` page with status 404 instead of Python's default error page
- [x] Given traffic arrives via Cloudflare → Caddy, when the contact rate limiter identifies a client, then it uses `CF-Connecting-IP` (falling back to the rightmost `X-Forwarded-For` hop, then the socket address) so the key cannot be spoofed by a client-supplied XFF
- [x] Given `server/contact.py` is committed, when deploy runs `git pull` on the server, then no untracked-file conflict blocks the deploy
- [x] Given the user systemd unit is installed by deploy, when the service starts, then it runs with `NoNewPrivileges=true` and `PrivateTmp=true` *(revised 2026-11-19: `ProtectSystem=strict` and the other capability-based options proved unenforceable in a user unit — exit 218/CAPABILITIES, ~2 min outage, fixed in `9bf0839`; full sandboxing remains available via the sudo-installed system unit, see runbook §10)*
